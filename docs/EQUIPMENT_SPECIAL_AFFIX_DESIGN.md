# 神将装备特殊词条系统设计

> 状态：设计方案，不代表已实现。
> 目标：解决神将装备只有基础属性、掉落之间缺少差异、装备无法匹配神将技能定位的问题。
> 关联文档：`docs/HERO_SKILL_EQUIPMENT_BUILD_DESIGN.md`。

## 一、设计结论

特殊词条不按某个神将 ID 写死，而是按技能机制标签生效：

`神将技能标签 → 流派标签 → 装备词条池 → 特殊词条被动技能 → 战斗触发事件`

这样同一件装备可以适配多个机制相近的神将，又不会变成所有角色都能无脑使用的通用最优解。

第一版规则：

- 每件装备继续保留现有基础属性、强化、精炼、觉醒、神铸和套装效果。
- 新增 1–3 条普通副词条，负责数值方向。
- 红色/高阶装备额外拥有最多 1 条“特殊词条”，负责改变战斗行为。
- 同名特殊词条全身只生效最高等级的一条，不重复叠加。
- 特殊词条分 T1/T2/T3 三档，只改变数值，不改变规则文本。
- 首版制作 12 个词条池、48 条特殊词条。
- 战斗界面必须显示特殊词条触发日志和单回合触发次数。

当前 `pet_equip.xml` 的60条模板全部是 `quality=4`，不能直接用现有品质字段决定词条档位。首版应使用掉落层级/装备星级生成 T1–T3，待装备品质体系正式拆分后再迁移到品质规则。

当前阵容运行时只统计位置1–4为神将装备，位置5/6属于法宝边界。配置中残留的戒指、鞋子模板不纳入首版特殊词条；法宝以后使用独立词条池。

## 二、为什么不能只增加普通数值词条

如果只添加攻击、生命、暴击、速度等属性，仍然会出现以下问题：

- 女娲和太乙都只追求治疗属性，复活流与溢疗流没有区别。
- 准提只堆生命，护盾守护与护盾爆破没有区别。
- 哪吒、金灵、恶来都只堆攻击暴击，追击、后排猎杀和击杀成长没有区别。
- 接引、吕岳、罗宣都只堆负面强化，禁疗、毒和灼烧没有区别。
- 黄飞虎、帝辛、无支祁都只堆生命，援护、嘲讽和反震没有区别。

所以装备必须同时拥有“数值副词条”和“机制特殊词条”。

## 三、装备实例结构

当前 `CEquip` 只保存 UID、模板 ID、经验、穿戴位置和养成等级，属性由模板与养成等级计算，没有实例词条字段。

建议增加：

```text
EquipAffixInstance
- affixId          特殊/普通词条ID
- tier             T1/T2/T3
- rollValue        本次随机数值
- locked           重铸锁定
- source           掉落/打造/迁移/转移
- generatedVersion 生成规则版本
```

`CEquip` 增加：

```text
vector<EquipAffixInstance> normalAffixes
EquipAffixInstance specialAffix
uint32 affixSeed
uint8 affixVersion
```

## 四、词条品类与部位池

### 4.1 普通副词条

| 分组 | 属性 |
|---|---|
| 攻击 | 攻击、物理/法术穿透、对首领增伤 |
| 防御 | 生命、物防、法防、免伤、被治疗 |
| 暴击 | 暴击率、暴击伤害、抗暴 |
| 频率 | 连击率、连击伤害、反击率、反击伤害、反震率、反震伤害 |
| 控制 | 命中、负面强化、负面抵抗、控制减免 |
| 速度 | 速度、开场行动、受治疗加速 |
| 持续 | 中毒、灼烧、流血伤害，异常目标增伤 |
| 治疗护盾 | 治疗效果、护盾效果、复活后生命 |

### 4.2 部位限制

| 部位 | 主要普通词条 | 允许的特殊词条方向 |
|---|---|---|
| 武器 | 攻击、穿透、异常增伤 | 爆发、追击、持续伤害、破盾 |
| 护肩 | 双防、抵抗、反击 | 援护、反击、控制抵抗 |
| 衣服 | 生命、免伤、被治疗 | 护盾、复活、分伤、反震 |
| 护腕 | 命中、暴击、连击、负面强化 | 控制、连击、触发强化 |

攻击类特殊词条不得出现在衣服，复活类不得出现在武器，以维持装备选择差异。速度、战意和治疗类词条分配到护腕、护肩或衣服，不新增装备部位。

## 五、48条首批特殊词条

实现等级：

- `C0`：可复用当前被动技能和现有触发事件。
- `C1`：需要增加少量战斗事件或统计字段。
- `C2`：依赖后续战意/战法系统。

## 七、词条生成与掉落规则

### 7.0 初版数值模板

具体数值需用固定种子战斗模拟校准，策划表先统一使用以下档位，避免每条词条各写一套尺度：

| 数值模型 | T1 | T2 | T3 | 适用效果 |
|---|---:|---:|---:|---|
| SMALL_PERCENT | 5% | 7.5% | 10% | 易伤、减伤、异常目标增伤 |
| MEDIUM_PERCENT | 10% | 15% | 20% | 护盾/治疗转化、追击强化 |
| PROC_CHANCE | 20% | 30% | 40% | 反击、控制延展、失手补偿 |
| MAX_HP_RECOVER | 2% | 3% | 4% | 嘲讽回血、反击汲取上限 |
| ACTION_SHIFT | 5% | 8% | 10% | 行动提前或延迟 |
| RAGE_VALUE | 2 | 3 | 4 | 单次战意获得 |

- CD减少固定为1回合，通过触发概率和每回合次数控制，不提升到2回合。
- 额外行动次数、复活次数、控制回合数不随T1–T3增加。
- 乘算型增伤统一进入一个特殊词条乘区；同类先相加再乘算，单角色初版硬上限30%。
- T3提升数值，不解除触发上限和互斥规则。

### 7.1 生成流程

1. 根据装备部位取得普通词条池。
2. 根据套装 `build_tags` 加权，但不排除其他流派。
3. 生成普通副词条，检查属性互斥。
4. 高阶装备生成一条特殊词条。
5. 特殊词条不得与装备固定套装效果完全重复。
6. 写入 `affixSeed` 和 `generatedVersion`，保证相同实例不会重复变化。

### 7.2 互斥规则

- 同一件装备不能同时出现攻击百分比与同属性更低级的固定攻击词条。
- 同一角色只能生效一条复活保护、一条额外行动和一条战意减耗。
- 追击、反击、连击产生的额外行动每回合总计不超过2次。
- 持续伤害扩散每回合最多一次。
- 控制延长对首领不增加控制回合，只转化为行动延迟。
- 同名特殊词条多件穿戴时只取最高等级。

### 7.3 重铸与转移

- 普通重铸：随机一条普通副词条。
- 定向重铸：选择词条类别，数值和具体词条随机。
- 特殊重铸：随机特殊词条，允许锁定当前普通词条。
- 特效提取：消耗原装备，把特殊词条转成一次性卷轴。
- 特效转移：同部位转移，保留目标装备其他属性。
- Steam单机版不设置每日次数，成本只用于控制成长速度。

## 八、旧装备迁移方案

不能在首次更新时静默随机改写玩家现有红装。

建议：

- 旧装备继续保持原属性，可正常使用。
- 每件已穿戴高阶旧装备发放一次“词条觉醒”选择，可从三个匹配套装的特殊词条中选一条。
- 背包旧装备第一次进入特殊重铸时才生成词条。
- 选择结果写入装备 UID，重复加载不得重新随机。
- 测试账号直接准备每类词条装备，用于验证59名神将推荐系统。

## 九、服务端与协议兼容设计

### 9.1 战斗实现

特殊词条映射为被动技能 ID，复用现有套装技能注入路径：

`装备词条 → passiveSkillId → 神将进入战斗 → passive_skill → trigger/additive effect`

当前38类技能触发事件已经可以直接承载攻击、行动、回合开始、受击、击杀、阵亡、护盾消失、治疗、攻击异常目标、开场增益等大部分 C0 词条。

需要新增的战斗上下文：

- 实际有效治疗量与溢出治疗量。
- 护盾实际吸收量和破盾来源。
- 伤害是否由援护、反击、反震、追击或持续伤害产生。
- 每个特殊词条的单回合、单目标和单场计数器。
- 后续战意值及战意来源事件。

### 9.2 存档兼容

现有装备存档是无版本的压缩二进制串。建议保留原有前缀不动，在整个装备/法宝旧数据末尾追加扩展区：

`magic=PXA1, version, recordCount, [equipUid, affixSeed, normalAffixes, specialAffix]`

新加载器先读取旧数据，再检测扩展区魔数；没有扩展区就是旧存档。落地前必须用 Cocos、Unity SQLite 和 MySQL 三条保存链验证旧客户端是否安全忽略尾部数据。

### 9.3 网络兼容

不直接修改旧装备列表包的逐件结构，避免旧 Cocos 客户端错位解析。

建议增加独立的“装备词条查询/重铸/转移”操作，按装备 UID 返回词条；Unity 接入新操作，旧客户端继续读取原装备列表。若以后要求 Cocos 同步支持，再通过协议版本协商扩展。

## 十二、验收标准

- 新掉落装备实例拥有稳定且可保存的词条，重登、重启、切号后不变化。
- 旧装备与旧存档不丢失、不自动随机改写。
- 特殊词条能通过装备 UID 查询、穿戴、卸下、重铸和转移。
- 同名词条、额外行动、持续伤害扩散和复活保护遵守叠加上限。
- 词条触发结果出现在战斗日志中，固定随机种子下可复现。
- 12名首批神将每名至少有两种推荐词条组合。
- 同一套基础装备更换特殊词条后，至少在两个机制首领中产生可验证的战术差异。
- 装备比较界面同时显示基础战力、流派匹配度、套装变化和特殊词条变化。
