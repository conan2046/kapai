# 全游戏统一任务与剧情系统设计边界

## 目标

全游戏只保留一套任务配置模型、一套事件类型目录、一套条件判定与任务状态机。剧情对话是任务流程中的一种节点或动作；主线、支线、日常、累计任务由同一模型配置和驱动。Steam 已屏蔽玩法的旧任务与事件只保留迁移审计记录。策划使用本地网页编辑器维护统一 Excel 源表，导出器分别生成服务端与各客户端所需格式。运行时任务进度、剧情选择和已播放状态由同一套服务端权威状态管理。

“统一”指配置语义和运行逻辑统一，不是把现有多份 Excel、XML、Lua、JSON 摆到一个网页中。现有表和 Lua 只作为迁移输入、兼容依据与核对证据；新内容不继续按旧路径增写。

## 统一数据模型

| Excel 表 | 用途 | 核心字段 |
|---|---|---|
| `EventType` | `EMQCT` 与 `daily.xlsx.condition[0]` 的去重事件目录 | `event_key`、中文名称、何时触发、如何计数、单位、归属范围、定义状态、Steam 范围与依据；屏蔽项不进入当前目录，待定义项不进入新任务条件选择 |
| `EventParam` | 每种事件的参数合同 | 所属事件、参数编号、中文名称、值类型、计数/筛选用途、可配置范围、比较方式、填写示例 |
| `QuestType` | 任务所属业务类型 | 固定为主线、支线、日常、累计四类；类型编号、中文名称、默认规则与说明 |
| `Quest` | 任务身份与生命周期 | `quest_id`、任务类型、旧列表分组、开放条件、重复周期、流程入口、显示规则 |
| `QuestCondition` | 任务对事件类型的引用和判定参数 | `quest_id`、阶段、`EMQCT` 事件编号、筛选值、比较符、目标值、逻辑组、计数起点、生效范围 |
| `QuestNode` | 任务事件流程与三个固定状态对话槽 | `node_id`、`quest_id`、节点类型、下一节点、对话状态、条件或对话组 ID |
| `DialogueLine` | 对话组中的逐句正文与表现 | 对话组 ID、行序、说话人、站位、正文、缩放、速度、延时、跳过 |
| `LegacyMap` | 只读迁移审计，不供策划选择 | 旧来源、旧任务/事件/剧情 ID、统一 ID、核对状态与证据说明 |

任务的事件流程保留 `Start → WaitEvent → Complete`。每条任务另有三个不可增删的 `Dialogue` 状态节点：未接取前、已接未完成、已完成未领取。节点只引用对话组 ID，不存单句正文；同一组 ID 可有多句，也可被多个任务复用。空引用表示该状态不播放对白。三个状态槽由任务状态选择，不是事件流程中依次执行的节点。选项分支、战斗演出等在有实际源链和需求时扩展。

`EMQCT` 本身是现行任务事件类型编号空间，`daily.xlsx` 和 `sevendays.json` 的 `condition` 第一位引用该类型。现有 `EMQCT` 定义 59 种，daily 引用 19 种，七日目标引用 22 种，两表合并实际引用 38 种且全部属于这 59 种。59 是旧编号目录规模，不代表语义归并后的最终可选事件数；例如法宝合成与图鉴品质事件仍需核对。任务阈值、每日或累计范围、奖励差异都只是任务引用时的参数，不生成新事件类型。当前按 Steam 范围区分为纳入 39 种、屏蔽 16 种、入口待核对 4 种；任务条件下拉框显示 43 种未屏蔽事件，其中 39 种可用于策划草稿，4 种入口待核对项可见但不可选。39 种中仅 9 种已有参数草稿；其余事件须补全合同并验收后才能用于正式导出。屏蔽项保留在迁移审计中，不随 Steam 任务导出。`EMISS_DC` 是另一套旧任务目标编号，保留在审计中；只有确认语义一致时才建立跨空间映射。完整核对见 `UNIFIED_QUEST_TYPE_EVENT_REVIEW.md`。

`daily.xlsx.type` 的 `0/1/2/3` 用于旧任务列表分组，服务端按它分桶，客户端按它请求列表；不能直接当成新任务类型。统一任务类型已固定为主线、支线、日常、累计。对白是适用任务的流程节点，任务是否使用事件目标由节点和条件决定，不是任务类型。

用户提供的另一款游戏样表验证了分层方式：`任务配置.xlsx` 的 `TaskPackage` 有 50 个任务包，`TaskType` 实际出现 1、6、7、22；表头注释说明 1 为章节任务、4 为每日任务、6 为限时任务、7 为生存者试炼活动任务，未解释 22，不能按编号猜测。`任务事件.xlsx` 的 `TaskDesc` 有 103 个带 `{0}` 等占位符的目标描述模板，并定义每个参数的含义与示例。它是目标/条件模板目录，不能不经语义核对就把每个模板 ID 等同于运行时事件类型。两份样表没有给出引用 `TaskDesc` 的具体任务明细表，不能仅凭任务包和目标模板还原完整任务实例。

`EMQCT_9` 是竞技场挑战，`EMISS_DC_9` 是神将招募；`EMQCT_59` 是加入帮派，`EMISS_DC_59` 是完成指定任务。迁移映射必须以 `legacy_system + legacy_id` 为联合键。Lua 中师门、周师门、寻宝、丹园等对 `EMISS_DC_59` 的多处调用，候选统一为带 `task_id` 参数的“任务完成”事件，不能仅凭调用名相同删除任何一个业务完成点。

## 单一运行链

1. 服务端业务在动作成功后发布一次带参数的统一事件，或更新一项权威状态。
2. 统一任务状态机只匹配当前有效任务及其条件，推进节点、记录进度与剧情选择。
3. 客户端从服务端接收统一的任务与剧情状态，用同一套导出数据渲染界面和对话；客户端输入只提交选择或交互，不自行判定奖励与完成。
4. 领取和完成操作由服务端按任务状态处理，保证重复请求不会重复推进或发放。

运行数据至少按角色或账号 ID、任务 ID、流程节点、进度、状态、周期实例、剧情选择和已播放标记存储。哪些任务按角色、账号或帮派生效，必须逐类从现有业务验证，不把所有任务强行放进同一作用域。

Steam 的任务与剧情入口采用功能按钮、任务追踪或流程节点打开对应 UI，不以 NPC 寻路/点击为默认前置。对话仍是统一任务流程中的节点，由 UI 展示并提交选择。旧 NPC 脚本的业务条件须先与当前 Steam 功能路由和服务端调用链核对，再决定迁移为事件、条件或历史数据；不能把旧 `NpcMain` 直接搬成新入口。代码链证据见 `UNIFIED_QUEST_LUA_AUDIT.md`。

## 网页编辑器的职责

策划主流程应从任务开始：选择或新建任务 → 选择业务任务类型并填写开放、前置、生效范围和周期 → 配置统一事件目标 → 在三个固定状态槽中按需选择对话组 ID → 预览、校验、保存到 Excel → 导出前后端格式。对话组内逐句内容在“对话组”页维护；事件库是任务目标选择时打开的统一目录。源代码位置、Lua 引用和旧 ID 映射放在独立迁移核对区。旧 Excel、Lua、XML 通过只读迁移工具导入和对照，不成为新内容的平行维护入口。网页与 Unity、Cocos 等引擎解耦；预览可在网页完成，最终玩家表现仍须在目标客户端验证。现有 `/editor` 已支持四类任务、事件目标和固定状态对话槽；游戏内播放与任务状态联动仍需验证。

## 迁移顺序与验收

1. 从当前表、`server/script/*.lua`、C++ 产生点和客户端入口建立全量映射台账，区分实际可达、历史休眠和仅配置存在。先核对事件类型与参数，再核对任务/剧情流程。
2. 定义统一 Excel 表和 ID 规则，给每条现存任务与剧情建立 `LegacyMap`。保留原始 ID 与数据快照，拒绝缺引用、编号冲突、不可达节点和无退出分支。
3. 建立统一事件派发与状态机，用选定的一条当前有效日常任务和一条章节剧情完成贯通验证。新旧路径并行记录结果时，不重复推进、播放或发奖。
4. 按玩法迁移其余当前有效任务，再处理休眠旧任务和 Lua 专用流程；每类验证触发、进度、重登、周期重置、剧情跳过与恢复。
5. 只有统一链覆盖并验证对应路径后，才删除该路径的旧条件分支、脚本任务硬编码与重复配置源。最后接入 Unity、Cocos 和其他引擎的导出适配器。

当前 Unity Editor 正在另一工作树中用于验收。本阶段只做源码/数据梳理、统一模型和独立网页工具；不启动 Unity，不写当前验收工作树或其运行配置。
