## 1. 结论与建议范围

**建议本次范围包含横版洞府主页、灵植园、聚灵阵、炼丹房、装备材料打造、藏书阁。** 先落实少量正式配方和完整产消闭环，再扩内容。法宝升品/洗练、五行灵根属于H盘旧方案的额外养成分支，调整为待核对扩展，不再默认与V1.3全部同时开发。藏书阁已由用户明确纳入，历史“首版不开发”结论撤销。

洞府是新增生产和养成系统，不能仅复制几张界面。必须同时闭合：资源来源与消耗、图纸学习、生产时间、操作协议、持久化、道具效果、属性与战斗、背包与邮件、入口和红点。

**推荐顺序：规则裁定与数据映射 → 共用协议/存档/生产任务基础 → 横版主页 → 灵植园 → 聚灵阵 → 炼丹 → 装备打造 → 藏书阁 → 跨模块回归。** 藏书阁的收集记录和属性合同在共用基础阶段建立，页面在后续完成，避免前期获得书籍漏记。逐模块闭环；具体数值和开工仍待用户核对。

## 5. 原项目前后端协议

## 15. 装备成品与材料打造并行方案

**已确认：低品质装备可直接给成品，高品质装备同时通过材料打造和直接掉落获得。** 材料打造提供定向补齐目标装备的能力，成品掉落继续保留直接获得装备的体验。建议把材料打造作为炼器室的独立装备页；具体品质分界、配方内容和产出量待核对，本轮尚未批准改正式表或开始业务开发。

旧装备锻造不能直接使用：旧 `UpdateCraftExp()` 将选中的其他装备 `TransforExp` 加到现有部位锻造经验，消耗装备、提升当前装备。新方案是消耗材料生成指定模板的装备实例，前后端字段、配方和背包结果均不同。

| 装备范围 | 获取流程 | 配置任务 | 当前结论 |
|---|---|---|---|
| 低品质装备 | 可直接获得成品 | 保留成品来源；具体品质范围待定 | 已确认可给成品，不强制先打造 |
| 高品质装备 | 直接掉落成品，以及收集材料后打造 | 两条来源分别配置，联合评估总供给；增加对应打造配方 | 已确认两条来源并行 |
| 材料获取 | 从正常玩法获得打造所需材料 | 反查已有掉落和奖励配置；确定材料名称、数量、来源和进度门槛 | 来源与产量待定，不默认取消现有成品掉落 |

不删除玩家已持有的装备，也不把未核对的奖励ID批量替换为材料。现有《DRAGON_CLIFF_CORE_GAMEPLAY_PLAN.md》已有“装备与材料并存、定向制造”的设计建议，本轮用户已明确获取方式；具体投放仍须逐源设计，不能借洞府恢复其余未批准系统。

**建议首版打造规则：**

- 玩家选择装备部位/目标模板，页面显示目标装备、所需材料、当前拥有量、解锁条件。
- 配方确定装备模板与品质，制作必成；不另加“材料扣了但制造失败”的概率。
- 若当前目标装备已有随机词条机制，按其已配置规则生成；未具备时先产出当前正式装备，不能仅为打造无意增加一套刷宝系统。
- 优先接当前 `equip.xlsx` 及装备实例模型，不移植旧项目3300个装备模板。主角/神将装备范围由用户指定。

- 完成后由服务端扣材并创建装备实例；满包走当前正式兜底方式，确定与邮件发放一致且不重复发奖。

| 新增配置/合同 | 建议字段 | 作用 |
|---|---|---|
| 装备打造配方 | recipe_id、output_equip_id、quantity、cost_items、unlock_condition、profession_exp、duration（如采用）、enabled | 明确材料、结果和开放条件；名称/字段在实施时冻结 |
| 材料掉落引用 | 当前掉落规则ID、原成品ID、目标材料ID、概率/权重、数量、适用条件 | 一条条解释成品如何改材料，不按名字批量替换 |
| 制作请求 | requestId、recipe_id、quantity、期望revision（如采用） | 不让客户端指定产物属性或提交“制造成功” |

**数值框架与校验，先定义测量口径，再填真实配置：**

设配方j消耗材料i为 `C_ij`，当前余额为 `B_i`，每次有效战斗/结算的期望掉落为 `r_i`。

`r_i = 各获得事件的概率 × 对应平均数量的合计`。互斥/多次抽取掉落按真实配置计算，不能把相对权重直接当最终概率。

`N_flux(j) = max_i(max(C_ij - B_i, 0) / r_i)`，只作为长期流量下的收集次数估算，不是随机掉落的保证次数或精确期望。需要的材料若 `r_i=0` 且没有其他来源，标记配方不可达。灵田来源计入对应时间产量后分别估算，不能把在线战斗次数与离线时间混成一个单位。

`资源净变化 = 战斗掉落 + 洞府生产 + 其他合法获得 + 返还 - 制造 - 洞府升级 - 其他消耗`。

| 校验项 | 通过条件 | 未具备输入时 |
|---|---|---|
| 第一件装备可达 | 初始能力能获得首份材料，配方解锁不依赖先穿该装备 | 标记阻塞，不能用测试GM资源代替 |
| 改造前后获取节奏 | 以同阶段/部位统计旧成品获得次数和新打造材料收集次数 | 不填虚构概率或成本；先抽正式掉落与装备池 |
| 品质/部位定向价值 | 明确新方案减少哪些无效重复掉落，稀有档位仍有目标 | 不把定向制造必然等同于更高品质 |
| 双来源总供给 | 高品质成品直掉与材料打造共同计入同阶段获取量，不将两条来源各自按原成品供给量配置 | 没有来源账本不调整掉落概率/材料数量 |
| 共用资源竞争 | 同阶段资源能支撑合理的洞府升级和装备目标 | 以旧材料图标复用代替重新平衡不合格 |
| 制造/分解循环 | 若加入分解，制造后返还不能产生净增材料/货币 | 明确锁定/穿戴与回收边界 |
| 随机收集波动 | 配方与掉落定稿后，检查P50/P90/P95收集次数与缺料尾部 | 只报平均材料供给不能当真实等待体验 |

理论参考为数值技能中“成本与时间、属性预算、期望成本、系统链条”的相关部分；本轮不套用竞品经验曲线，不新增装备属性预算或擅改当前战斗公式。

**施工顺序：** 明确品质分界与装备范围 → 审计现有成品来源及旧存档 → 配方/材料/解锁设计 → 材料正常获得来源接入 → 后端打造/存档 → 炼器装备页 → 联合配置成品直掉与材料产出 → 主线获取节奏和用户实际体验验收。高品质成品来源保留；材料供给与打造能力一起闭环。

|---|---|---|
| 单本奖励 | 指定书目首次收集满足对应奖励条件 | 每书独立book_id；重复副本不反复获得同一永久奖励 |
| 多本奖励 | 同套收集k本，或集齐指定book_id列表 | k≤N，指定列表必须属于该套；支持不同套不同门槛 |
| 整套奖励 | 收集全部N个有效书目 | 完整度从书目集合计算，不用道具数量累加冒充 |
| 激活 | 条件满足→可激活→后端确认→已激活 | 建议手动激活及入口红点；自动激活另定，达到条件不等于页面擅自加属性 |
| 重复书籍 | 不增加不同书目完成度 | 重复道具仍按背包合同管理；是否兑换/分解另定 |
| 收藏永久性 | 首次合法获得即记录历史收集，激活后持续有效 | 建议出售/消耗书籍不撤销收藏和已激活效果；是否需要学习书籍后才收藏待定 |
| 属性叠加 | 每奖励行记录独立增量，激活后相加 | 若采用累计档位，必须只加差值或取最高档；禁止累计总值再次相加 |
| 效果对象 | 上阵神将，已由用户确认 | 接当前神将属性与战斗计算链；建议换阵后对新上阵神将生效，退阵者不继续携带此阵容加成 |

建议配置分为 `BookDefinition(book_id,item_id,set_id,name,icon,unlock)`、`BookSet(set_id,name,book_ids,sort/filter)`、`BookReward(reward_id,set_id,condition_kind,required_count/required_book_ids,attribute_deltas)`。一书是否跨套、指定组合能否叠加数量档位须明确；推荐首版一书归一套，所有独立奖励可累计。套大小从有效书目列表派生或校验N一致，不能只填一个N却缺少书籍定义。

建议协议语义：`BookCollectionInfo` 返回书目历史、各奖励条件/激活状态、已生效属性和revision；`ActivateBookReward(requestId,reward_id)` 在后端检查条件并记录唯一激活，返回完整变化与权威属性。编号/正式名称实施阶段分配。获得书籍时挂接服务端正常奖励、购买、制作及背包获得链；页面打开不登记虚假收集，不通过客户端上报“已获得”直接授奖。领取邮件与首次入包的登记时点需统一，避免同一本漏记或重复记。

SQLite建议独立记录 `(角色,book_id,首次获得时刻)` 和 `(角色,reward_id,激活时刻)`，各有唯一约束；激活事务包含去重与属性状态更新。永久加成按已激活奖励重建：`藏书加成[a] = Σ 已激活reward的attribute_delta[a]`，重登时重建派生值，不再次把相同奖励加到基础属性。旧档初始化为空；若历史书籍没有获得日志，须决定按现有背包回填范围，不能声称可恢复已出售书籍。不同Slot互不污染。

界面采用用户图鉴参考：左侧品质/境界/状态筛选与属性总览，中部书套列表及收集进度，右侧书目状态、奖励条件及激活按钮；整套完成与所有奖励已激活分开显示。一次获得多本跨越多个门槛时，所有满足但未激活的奖励均能操作。图片中的功法点、功法积分、图鉴等级、评分与“前往修炼”不自动增加；收藏书籍不等于新增可装备功法和技能修炼系统。

现有 [HeroBookStore.cs](E:/neiwang_kapai/Game/unityclient/Assets/src/Data/HeroBookStore.cs) 已有神将图鉴条目、评分、属性及权威状态结构，可参考其状态刷新与UI组织；它的数据对象是神将/星级，不能把书套写入神将图鉴状态。H盘GongFa表仅定位到文件名，尚未确认存在可直接复用的套书/门槛字段；正式书籍道具、图标和套关系仍需S01逐项映射。

验收重点：每套不同N；单本/数量/指定组合/全套；重复副本；一次跨多个门槛；满足条件未激活时不生效；激活永久且重登不重复加；书籍出售/使用后的历史状态；真实战斗/修炼效果、Slot切换及图鉴红点。奖励数值未在本轮虚构。
